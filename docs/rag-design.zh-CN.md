# RAG 设计说明

## 目标

这个助手的目标是：在回答兔子护理和健康相关问题时，先检索领域知识，再将检索到的内容作为大语言模型的上下文。

核心设计目标是 **grounding（基于依据生成）**：最终回答应尽可能由相关检索材料支持，而不是只依赖模型本身已有的通用知识。

## 整体流程

```text
1. 用户提交问题
2. 系统对问题进行检索前处理
3. 从知识库中检索相关知识片段
4. 将检索结果整理为模型上下文
5. LLM 基于上下文生成回答
6. 在测试中同时检查检索质量和回答质量
```

## 为什么使用 RAG

兔子护理问题往往比较具体，相关信息可能分散在不同资料中，也可能存在不同表达方式。通过增加检索层，可以在回答时动态给模型提供更聚焦的领域信息，而不是完全依赖模型已有知识。

## 设计重点

### 检索相关性

一个回答即使语言流畅，如果检索到的上下文本身不相关，最终结果依然可能不可靠。因此，检索质量被当作系统中的核心问题，而不是辅助步骤。

测试问题会覆盖：

- 日常护理类问题
- 更具体的健康相关问题
- 用不同说法表达同一概念的问题

### 上下文质量

检索到的 chunk 需要包含足够的信息来支持回答，同时又不能引入太多无关内容。

这会涉及到实际的调优问题，例如：

- 文档应该如何切分
- 每次应该检索多少上下文
- 检索结果与用户真实意图是否匹配
- 是否需要补充相邻上下文以保证信息完整

### 基于检索内容生成回答

回答阶段应优先使用检索得到的上下文作为依据。

在开发过程中，会同时查看“检索到了什么”和“模型最终回答了什么”，从而区分问题到底出在检索阶段，还是生成阶段。

## 当前关注的失败情况

RAG 系统中常见的问题包括：

- 多个高度相似的 chunk 被重复召回
- 语义上相关，但实际对当前问题帮助不大的内容排名过高
- 关键支持信息没有被检索出来
- 用户问题过于宽泛，一次检索不足以覆盖
- 模型生成了超出检索依据范围的内容

项目目前会围绕这些失败案例持续调整，而不是只验证成功样例。

## 保持私有的内容

这个公开展示仓库不会包含：

- 完整应用源码
- 私有知识库内容
- API Key 与环境配置
- 生产使用的 Prompt
- 检索索引或 Embedding 数据

公开仓库主要用于展示系统架构与开发方法。
